## Latest (2026-10-22)

- **Custom scrollbars (vertical and horizontal)** in the file list: `ScrollThumb` is a control of its own that sits on top of the list's native bar and paints the window's design — dark track, rounded gradient thumb (Cyan→Violet on hover/drag), grip lines when there is room, RTL mirrored. A click on the track jumps there, the thumb can be dragged, the wheel over the bar still scrolls the list, files can be dropped on it. Each bar is shown only while its axis really scrolls; the vertical bar shortens when the horizontal one appears. The list is scrolled with `LVM_SCROLL` (pixels; rows × row height for the vertical axis) because a ListView ignores `WM_VSCROLL` thumb tracking. `/selftest` exit 31 checks the thumb geometry (`ThumbOf`).
- **Less UI work while copying**: the list no longer repaints every visible row four times a second. `MainForm.RepaintChangedRows` invalidates only the rows of the files being copied and rows whose state changed (`CopyItem.PaintedState`), with a full repaint kept as a 5 s safety net and whenever the row count, the busy state or the error count changes. Virtual-mode rows (`CopyItem.Row`), the formatted size (`SizeText`) and the row→item lookup of one row (reused for its five other cells) are no longer rebuilt on every paint. Measured with instrumentation on a 4.2 GB / 32-file copy: painted cells 287–339/s → 59/s (one run 0/s). Total process CPU stayed the same within noise because the copy itself dominates.
- **Verified**: build (v3.5 csc) + `/selftest` exit 0 for the build and the installed copy; live 200-file window driven with window messages — vertical track click pos 125→187, vertical drag 156→113, window shrunk → horizontal bar appears and the vertical one shortens, horizontal click 0→18, horizontal drag 18→0; no stray processes, `settings.ini` restored.
- **Verification got ~45% cheaper**: XXH3 is the default (`Verify=1`) and was the dominant CPU cost of any copy — a 1.6 GB copy spent 9.8–10.1 s of CPU with it on against 1.7 s with it off. The pass: word reads via `BitConverter` on little-endian instead of eight byte loads, the secret pre-read as 64-bit words for the aligned offsets used by the hot loop, 64 KB reads instead of one 1024-byte read per block, and one buffer set per thread (`[ThreadStatic]`) instead of a fresh block buffer, tail buffer and accumulator for every file. Same 1.6 GB copy now 5.3–5.5 s CPU, wall 8.8–10.1 s (was 12.2–12.8 s). All known-answer vectors (empty/abc/16/17/128/240 bytes, 241/1024/1025/3000-byte files) still pass.
- **Timer only runs fast when it has something to do**: 250 ms while a job runs, 1 s while idle; the queue poll and the auto-close delay now use the clock instead of tick counts, so a slower timer does not delay hand-off (still ~1 s) or auto-close (~2.8 s). Idle UI ticks measured with instrumentation: 20 per 5 s → 5 per 5 s.
- **Hover/repaint oddities in the list**: back to a fresh `ListViewItem` per retrieved row (the control keeps hover/focus/selection state on the item object; a shared instance showed it on the wrong row), `lv_DrawItem` fills the row background so an item-level repaint cannot leave stale pixels, and the active-row follow is suppressed for 2.5 s after the user scrolls instead of while the pointer happens to be over the list (which froze the follow and made the list jump when the pointer left).
- Limits: the scrollbar look was verified through its geometry, the scroll positions and the control rectangles, not by inspecting pixels; the error-report dialog still uses the native TextBox scrollbars.

## Safety pass (2026-10-21)
- Review of the whole program (engine, window, helper) with the fixes applied right after: engine - a source that vanished is an error, the destination is set aside under a unique name and always restored on failure, the copy length is checked even without hash verify, two items with the same destination are serialized by a per-destination lock, a failed robocopy run is an error and not a "cancelled", the scan and every worker have a top-level catch, the buffer allocation survives an `OutOfMemoryException`.
- Window - the conflict dialog preselects "skip" (Enter never destroys a file), stays on top, and cancelling it skips the other waiting files too (`Settings.AskGen`); the close button cancels the workers and closes the window later instead of freezing the interface for 3 s; the close question defaults to the safe answer; Pause/Cancel act on the running job; "Reset to default" only fills the controls, so Cancel really cancels; the admin prompt keeps the failed job across the modal dialog; the timer is stopped around modal dialogs.
- Helper - the cut/copy flag is read from locked clipboard memory (`GlobalLock`), long paths are no longer cut short (`DragQueryFile` length first), `Ctrl+V` is only swallowed when the clipboard really holds files, the hook result and the paste path are checked, `settings.ini` is written atomically (`File.Replace`), the autostart entry only ever points at the installed copy, an unknown command line option is reported instead of silently starting the helper.
- Queue - a job file is claimed by moving it, so two windows can never run the same job; stale claims from a crash are cleaned up after 10 minutes.
- Self-check: `/selftest` exit 24 (a vanished source is an error and nothing is written) and exit 25 (a failing copy puts the old destination back and leaves no backup file); build green; E2E copy + move through the queue verified; installed copy refreshed, `/selftest` exit 0, helper running.
